Seção 5 — Riscos Técnicos e Decisões Críticas

O que pode dar errado e como mitigar antes de começar

ALTO Vazamento cross-tenant por query sem guard

Um endpoint que esqueça o filtro WHERE organization_id = ctx.orgId expõe dados de outras igrejas. É o risco mais grave do row-level isolation.

Mitigação: Criar uma classe base BaseRepository que injeta organization_id automaticamente em todo select/insert/update. Repositórios só herdam dela — nunca constroem queries cruas. Testes de integração verificam que nenhum endpoint retorna dados de outra org.
MÉDIO Better Auth Organizations — compatibilidade com hierarquia customizada

O plugin suporta roles customizadas, mas a hierarquia de 6 níveis com visibilidade em cascata (Pastor de Rede vê só sua rede) vai além do que o plugin oferece nativamente.

Mitigação: Better Auth armazena o papel (string). A lógica de hierarquia e visibilidade fica inteiramente no PermissionResolver da aplicação — o plugin só gerencia memberships e sessions. Fazer um spike técnico na Phase 8.5 para confirmar integração antes de commitar.
MÉDIO Migração de dados existentes

O banco atual tem dados sem organization_id. Adicionar a coluna como NOT NULL quebra a migration. Se houver dados de teste reais, precisam de uma org "seed".

Mitigação: Migration em duas etapas — (1) adicionar coluna como nullable + criar org seed + backfill, (2) tornar NOT NULL. Script de backfill deve ser idempotente e testado em ambiente de staging antes da produção.
MÉDIO Cache cross-tenant no frontend

Se o usuário trocar de organização e o TanStack Query não invalidar o cache, ele vê dados da org anterior.

Mitigação: Todas as query keys incluem orgId como prefixo — ex: ['org', orgId, 'eventos']. Ao trocar de org, chamar queryClient.clear() para limpar todo o cache da sessão anterior.
BAIXO Performance sem índices compostos

Queries com WHERE organization_id = X em tabelas grandes ficam lentas sem índice.

Mitigação: Criar índice em (organization_id, id) e (organization_id, created_at) nas tabelas principais na própria migration da Phase 8.5. Baixo risco no estágio atual — volume é pequeno.

Decisões que precisam ser tomadas antes de codar

Como o Pastor de Rede enxerga "sua rede"?

Ele vê todas as pessoas da org, ou só as que foram explicitamente linkadas a ele? Definir antes de modelar a visibilidade hierárquica.

Onboarding: org criada por quem?

Qualquer usuário pode criar uma org e vira Presidente automaticamente? Ou há um step de verificação? Para v1.0: self-service livre — quem cria é owner.

Um usuário pode ser membro de múltiplas orgs?

Better Auth suporta isso nativamente. É útil para pastores que atuam em mais de uma igreja. Recomendado: sim, com org "ativa" na sessão.

Pessoa (cadastro) = Usuário (login)?

Atualmente, pessoas e users (Better Auth) são entidades separadas. Definir se/como elas se relacionam — um membro precisa ter login?
