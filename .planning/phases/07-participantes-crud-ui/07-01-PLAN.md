# 07-01 - Backend participant full-update contract

<objective>
Add the missing backend contract that lets the Phase 7 UI edit a complete participant record, while preserving the existing focused health endpoint, soft-delete semantics, RBAC, and auditability for sensitive participant data.
</objective>

<requirements_addressed>
- UI-PES-02: Users can create/edit participants with complete personal, health, and emergency data.
- UI-PES-04: Users can inactivate participants with soft-delete and history preservation.
</requirements_addressed>

<truths>
- D-07: Backend changes are allowed only when strictly needed for participant CRUD.
- D-08: UI edit appears as one complete form experience even if backend work is broken into technical pieces.
- D-10: Write actions must reflect current role restrictions.
- D-11: Inactivation must remain soft-delete with preserved history.
- D-14: Use existing shared pessoa fields and avoid inventing new fields.
</truths>

<threat_model>
| Threat | Severity | Mitigation |
|--------|----------|------------|
| A non-lider user updates participant health or emergency data | HIGH | New route uses `requireRole('lider')`; tests must include authorized update path and route must not use plain `authMiddleware` only. |
| A broad update silently bypasses audit requirements for health fields | HIGH | `UpdateParticipanteUseCase` receives `AuditLogRepository` and writes action `UPDATE_PARTICIPANT` with changed field names/payload after successful update. |
| Update modifies a soft-deleted participant | MEDIUM | Use `and(eq(pessoas.id, id), isNull(pessoas.deleted_at))` in the update `where` clause. |
| Frontend receives successful response for a missing participant | MEDIUM | If update returns no row, throw `Participante not found` so controller maps to an error response. |
</threat_model>

    <action>
      Add `apps/api/src/modules/pessoas/usecases/UpdateParticipanteUseCase.ts`.
      Define an `UpdateParticipanteData` type with exactly these optional fields: `nome`, `genero`, `data_nascimento`, `telefone`, `email`, `padrinho_id`, `alergias`, `restricoes_alimentares`, `medicamentos`, `condicoes_medicas`, `contato_emergencia_nome`, `contato_emergencia_tel`.
      Implement `execute(id: string, user_id: string, data: UpdateParticipanteData)`.
      Before updating, if `data.email` is present, query `pessoas.email` for another row with the same email and a different id; throw `Email already exists` when found.
      Before updating, if `data.telefone` is present, query `pessoas.telefone` for another row with the same phone and a different id; throw `Phone already exists` when found.
      Update `pessoas` with `{ ...data, updated_at: new Date() }` using `where(and(eq(pessoas.id, id), isNull(pessoas.deleted_at)))` and `.returning()`.
      If no row returns, throw `Participante not found`.
      After a successful update, call `auditLogRepo.logAction({ user_id, target_id: id, action: 'UPDATE_PARTICIPANT', changes: data as any })`.
      Return the updated participante row.
    </action>
