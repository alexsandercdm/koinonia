# 07-02 - Participant hooks and record sheet components

<objective>
Create the reusable frontend data and component layer for participant list/search, create/edit, history, and soft-delete actions before wiring the full page.
</objective>

<requirements_addressed>
- UI-PES-01: List/search participants from cached server state.
- UI-PES-02: Create/edit participant through a complete three-tab form.
- UI-PES-03: Show participant event history.
- UI-PES-04: Inactivate participant through soft-delete.
</requirements_addressed>

<truths>
- D-03: CTA and "Ver ficha" open a sheet/drawer with Dados, Saude, Emergencia tabs.
- D-04: Search responds first from cached client data.
- D-05: Frontend treats participant list as paginated `data` + `pagination`.
- D-06: Mutations invalidate or update participant and history query keys consistently.
- D-09: History appears in the same ficha experience.
- D-13: Field validation appears inline before final submit.
- D-14: Use existing shared schemas/DTOs and avoid new fields.
</truths>

<threat_model>
| Threat | Severity | Mitigation |
|--------|----------|------------|
| Health data remains visible in stale cache after edit/delete | HIGH | Update/invalidate `participantesKeys.lists()`, `participantesKeys.detail(id)`, and relevant history/detail caches after mutations. |
| Form submits fields not accepted by the backend | MEDIUM | Payload builder only emits keys from `CreatePessoa` / `UpdatePessoa`; no UI-only `papel`, `quarto`, or `setor`. |
| Unauthorized user sees enabled destructive controls | MEDIUM | Components accept `canWrite` and `canDelete` booleans derived from role in the page; disabled state has visible explanatory text. |
</threat_model>

      Import `useQuery`, `useMutation`, and `useQueryClient` from `@tanstack/react-query`.
      Import `apiFetch` and `ApiListResponse` from `../lib/api`.
      Import `CreatePessoa`, `UpdatePessoa`, and `Pessoa` from `@koinonia/shared`.
      Define `ParticipanteListParams` with optional `q`, `page`, and `pageSize`.
      Define `ParticipanteHistoricoItem` with `evento` and `inscricao` fields typed minimally from the current API response.
      Export `participantesKeys` with `all`, `lists`, `list(params)`, `detail(id)`, and `historico(id)`.
      Implement `useParticipantes(params: ParticipanteListParams = {})` with query key `participantesKeys.list(params)`, query function `apiFetch<ApiListResponse<Pessoa>>('/api/v1/participantes?...')`, default `page=1`, default `pageSize=100`, and `staleTime: 1000 * 60 * 5`.
      Implement `useParticipante(id: string, enabled = true)`.
      Implement `useParticipanteHistorico(id: string, enabled = true)`.
      Implement `useCreateParticipante`, `useUpdateParticipante`, and `useDeleteParticipante`.
      `useCreateParticipante` posts to `/api/v1/participantes`.
      `useUpdateParticipante` patches `/api/v1/participantes/${id}` with `UpdatePessoa`.
      `useDeleteParticipante` deletes `/api/v1/participantes/${id}`.
      On create/update/delete success, invalidate `participantesKeys.lists()`. On update success, also invalidate `participantesKeys.detail(id)` and `participantesKeys.historico(id)`. On delete success, remove or invalidate `participantesKeys.detail(id)`.
