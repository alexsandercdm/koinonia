# Phase 6.5: Frontend Redesign Migration - Research

**Researched:** 2026-04-26
**Status:** Ready for UI design contract
**Question:** What do we need to know to plan this phase well?

## Research Summary

Phase 6.5 is a structural frontend migration, not a feature expansion. The implementation should replace the Phase 5 dark Stitch baseline with the `doc/Koinonia-redesign` "Hallowed Weight" direction while preserving every live runtime contract: Better Auth session handling, `ProtectedRoute`, TanStack Query usage, persisted cache behavior from Phase 6, and existing navigation routes.

The safest plan shape is a layered migration:

1. Convert global visual tokens first in `apps/web/src/index.css` and `apps/web/tailwind.config.js`.
2. Extend or restyle existing UI primitives before page rewrites.
3. Replace `AppLayout` with the light responsive shell and event-context header.
4. Migrate login and authenticated pages incrementally, preserving hooks and data contracts.
5. Verify responsive behavior, auth/session continuity, and build/type health.

## Canonical Design Findings

### Hallowed Weight Direction

The new design direction is light, restrained, and editorial:

- Warm application background: `#F7F4EF`.
- Primary text foundation: `#1A1612`.
- Main surface: `#FFFFFF`.
- Raised surface: `#FDFCFA`.
- Warm borders: `#E8E3D9` and `#CFC8BB`.
- Secondary text: `#7A7060`.
- Tertiary text: `#B0A898`.
- Scarce gold accent: `#C4923A`, with `#F5ECD9` and `#EDD8AD` for focus/subtle states.
- Status palette:
  - Success: `#3D7A52` / `#E8F4ED`
  - Warning: `#B07030` / `#FBF0E2`
  - Danger: `#9B3A2E` / `#FBECEC`
  - Info: `#2E628B` / `#E8F2FA`

The Phase 5 dark-violet tokens in `.planning/design/UI-SPEC.md`, `apps/web/src/index.css`, and `apps/web/tailwind.config.js` are stale for Phase 6.5. The code still uses classes such as `bg-background-dark`, `bg-surface-dark`, `border-border-dark`, `text-slate-*`, `text-violet-*`, and `amber-accent`; the migration should convert these into semantic warm-light tokens instead of scattering literal hex values through page components.

### Prototype-to-Runtime Translation

The redesign files are JSX/inline-style prototypes, not production React modules. They should be translated into Tailwind and existing component patterns:

- `koinonia-primitives.jsx` defines the target primitives: `Badge`, `Btn`, `Input`, `SelectInput`, `TextArea`, `FormField`, `Card`, `Drawer`, `EmptyState`, `SectionTitle`, and `FilterTabs`.
- `koinonia-layout.jsx` defines the target shell shape: sidebar, compact header, `EventPill`, page title, page actions, and event context.
- `koinonia-pages-main.jsx` shows dashboard, participant list/drawer, inscription, and finance visual hierarchy.
- `koinonia-page-login.jsx` is the source for the new editorial login layout.
- `koinonia-page-acomodacoes.jsx` is the source for accommodation map/structure visual migration.
- `koinonia-data.jsx` defines useful status mappings and semantic color relationships.

The planner should treat these files as visual contracts and source semantics, not copy-paste implementation.

## Runtime Code Findings

### Layout and Navigation

`apps/web/src/components/layout/AppLayout.tsx` is the central migration point. It currently:

- Uses a fixed desktop sidebar with `h-screen` and `overflow-hidden`.
- Depends on dark tokens: `bg-background-dark`, `bg-surface-dark`, `border-border-dark`, and white/slate text.
- Preserves authenticated user context and logout via `useAuthContext`.
- Provides route navigation through `useNavigate` and active state via `useLocation`.
- Accepts `title` and `actions`, which is compatible with the redesign header model.

The redesigned shell should preserve `NAV_ITEMS`, `useAuthContext`, `logout`, route paths, and the `title/actions` API. Mobile must not depend on the fixed sidebar. A drawer or compact bottom/top navigation is acceptable if `/dashboard`, `/participantes`, `/inscricoes`, `/acomodacoes`, and `/financeiro` remain reachable.

### Auth and Session

`apps/web/src/App.tsx` wraps the app with `QueryClientProvider` and `AuthProvider`, then protects all feature routes with `ProtectedRoute`. `apps/web/src/pages/login.tsx` uses `useAuthContext().login`, redirects to `/dashboard`, and shows real loading/error states. `apps/web/src/lib/api.ts` calls Better Auth via `authClient.getSession()`, redirects 401/unauthenticated users to `/login`, and throws `ApiError` with numeric status.

Phase 6.5 must not alter auth mechanics unless the change is purely visual. Verification should include login/register/protected route smoke coverage if feasible.

### Current Pages

The pages already use live hooks and API contracts:

- `dashboard.tsx` queries participants, finance metrics, events, and recent inscriptions.
- `ParticipantsPage.tsx` queries `/api/v1/participantes`, filters locally, and contains loading/error/empty logic.
- `InscricoesPage.tsx`, `AcomodacoesPage.tsx`, and `FinanceiroPage.tsx` must be migrated visually while retaining hooks and existing domain behavior.
- Accommodation components under `apps/web/src/components/acomodacoes` are operationally sensitive and should be restyled without changing assignment/export logic.

The planner should avoid new CRUD behavior. Phase 7 owns participant CRUD completion; Phase 8 owns events CRUD; Phase 9 owns inscription/payment workflow; Phase 10 owns accommodation offline hardening.

## Recommended Plan Breakdown

### Plan 06.5-01: Design Tokens and Primitives

Purpose:
- Replace dark-violet/stitch tokens with Hallowed Weight tokens.
- Add/adjust reusable UI primitives before page-level migration.

Likely files:
- `apps/web/src/index.css`
- `apps/web/tailwind.config.js`
- `apps/web/src/components/ui/button.tsx`
- `apps/web/src/components/ui/card.tsx`
- `apps/web/src/components/ui/input.tsx`
- `apps/web/src/components/ui/label.tsx`
- `apps/web/src/components/ui/sheet.tsx`
- New primitives only if needed, under `apps/web/src/components/ui`.

Risks:
- Broad token renames can break existing class names if pages are not migrated in the same phase.
- Tailwind config currently uses `require("tailwindcss-animate")` in an ESM config; avoid unnecessary config style changes.

Verification ideas:
- `pnpm --filter web type-check` or project equivalent.
- `pnpm --filter web build`.
- Grep for stale dominant tokens after migration: `background-dark`, `surface-dark`, `border-dark`, `amber-accent`, `#4d0085`, `#1b0f23`, `#ffbf00`.

### Plan 06.5-02: Responsive App Shell and Auth Screens

Purpose:
- Replace `AppLayout` with the light shell, responsive navigation, header actions, and visual event context.
- Migrate login/register visuals while preserving Better Auth behavior.

Likely files:
- `apps/web/src/components/layout/AppLayout.tsx`
- `apps/web/src/pages/login.tsx`
- `apps/web/src/pages/register.tsx`
- Possibly a new small `EventPill` or navigation subcomponent under `apps/web/src/components/layout`.

Risks:
- Breaking `logout`, route navigation, active route state, or protected route expectations.
- Introducing event selection that implies backend behavior before Phase 8. Keep it visual/local or read-only.
- Mobile navigation must expose all routes without layout overlap.

Verification ideas:
- Auth smoke: unauthenticated feature route redirects to `/login`.
- Login form still calls `login(email, password)` and navigates to `/dashboard`.
- Register route still exists.
- Playwright/manual viewport checks at 390px and desktop width for shell/login.

### Plan 06.5-03: Dashboard, Participants, Inscriptions, and Finance Visual Migration

Purpose:
- Migrate current dashboard and administrative list/metric screens to the light system without adding CRUD scope.

Likely files:
- `apps/web/src/pages/dashboard.tsx`
- `apps/web/src/pages/ParticipantsPage.tsx`
- `apps/web/src/pages/InscricoesPage.tsx`
- `apps/web/src/pages/FinanceiroPage.tsx`

Risks:
- Accidentally replacing live query data with prototype mock data.
- Dropping loading/error/empty states while restyling.
- Desktop tables can become unusable on mobile if no responsive alternative is planned.

Verification ideas:
- Existing route files still call `apiFetch`/hooks with current endpoints.
- Each page keeps loading, error, and empty/data states.
- Mobile layout uses responsive cards or controlled overflow instead of fixed-width tables.

- Run the broad frontend verification pass for Phase 6.5.

Likely files:

- `apps/web/src/components/acomodacoes/CamaCard.tsx`
- `apps/web/src/components/acomodacoes/AssignCamaSheet.tsx`
- `apps/web/src/components/acomodacoes/MapaQuartosGrid.tsx`

Risks:

- Visual status colors must remain semantically clear for available/occupied/blocked/conflict states.

Verification ideas:
- Accommodation E2E if feasible.
- Build/type-check.
- Manual or screenshot checks for `/acomodacoes` on mobile and desktop.

## Plan Constraints

The planner should require every implementation plan to preserve:

- Better Auth integration in `apps/web/src/lib/auth.ts`, `AuthProvider`, `ProtectedRoute`, and login/register pages.
- Current route paths: `/dashboard`, `/participantes`, `/inscricoes`, `/acomodacoes`, `/financeiro`, `/login`, `/register`.
- TanStack Query usage for server state.
- Phase 6 persisted cache behavior.
- Existing backend API paths and payload assumptions.
- No new dependencies unless a plan explicitly proves existing Tailwind/primitives cannot solve the need.
- No new domain capabilities that belong to Phases 7-10.

## Validation Architecture

Recommended validation for Phase 6.5 planning:

1. Static verification:
   - Type-check the web app.
   - Build the web app.
   - Grep for stale dominant Phase 5 tokens and class names.
2. Behavioral verification:
   - Auth routes still render and redirect correctly.
   - Protected feature routes remain guarded.
   - Dashboard and feature pages still use live hooks/API clients.
3. Responsive verification:
   - Check 390px mobile, tablet-ish, and desktop widths for shell, login, dashboard, participants, and accommodations.
   - Confirm navigation remains reachable without fixed sidebar dependence.
4. Accessibility/operational verification:
   - Critical action targets remain at least 44px where feasible.
   - Loading/error/empty states still exist on migrated pages.
   - Text does not overflow buttons, cards, tables, or mobile nav.

## Planning Risks

- Existing `.planning/design/UI-SPEC.md` is stale and still describes the dark Stitch design. A phase-local UI-SPEC is needed before final PLAN.md generation because this phase is explicitly a frontend redesign migration and `workflow.ui_safety_gate` is enabled.
- The design prototypes use inline styles and mock data; plans must forbid replacing runtime data with mocks.
- The current `AppLayout` is a single high-leverage file. Shell migration should happen before page migrations, but pages must still be updated in the same phase to avoid mixed visual systems.
- The current login includes external imagery and decorative gradients/orbs that conflict with the new editorial direction and the frontend guidance. Plans should prefer a clean editorial split using warm surfaces and real auth controls.
