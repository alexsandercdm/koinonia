# Phase 6.5: Frontend Redesign Migration - Context

**Gathered:** 2026-04-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Migrar o frontend existente para o novo design em `doc/Koinonia-redesign` antes da Phase 7, porque a mudança é estrutural: novo visual system, novo shell, novo comportamento responsivo e novo baseline de componentes. Esta fase não deve implementar CRUDs novos; ela prepara o terreno visual e responsivo para as fases funcionais 7-10.

</domain>

<decisions>
## Implementation Decisions

### Direção visual
- **D-01:** O redesign em `doc/Koinonia-redesign` substitui o baseline visual Stitch da Phase 5 para as próximas fases de frontend.
- **D-02:** A estética principal é "Hallowed Weight": clara, editorial, espaçosa, precisa e contida, com preto/marrom profundo como fundação, branco quente como superfície e ouro usado com parcimônia.
- **D-03:** Tokens canônicos iniciais: `bg #F7F4EF`, `surface #FFFFFF`, `surfaceRaised #FDFCFA`, `border #E8E3D9`, `borderStrong #CFC8BB`, `text #1A1612`, `textSec #7A7060`, `textTer #B0A898`, `gold #C4923A`.
- **D-04:** O violet/dark mode da Phase 5 deixa de ser o padrão visual. Não remover suporte técnico a temas se ele existir, mas a entrega principal deve ser clara e quente.

### Arquitetura de UI
- **D-05:** Converter o protótipo JSX/inline-style em componentes React/Tailwind reais, não copiar os arquivos do protótipo diretamente para runtime.
- **D-06:** Criar ou adaptar primitives reutilizáveis para `Badge`, `Button`, `Input`, `Select`, `TextArea`, `FormField`, `Card`, `Drawer`, `SectionTitle`, `FilterTabs` e `EmptyState`.
- **D-07:** Primitives existentes em `apps/web/src/components/ui` devem ser reaproveitadas quando possível, mas podem receber variantes/tokens novos para evitar duplicação.
- **D-08:** O planner deve privilegiar CSS variables/Tailwind theme para tokens globais em vez de espalhar hex values pelas páginas.

### Shell, navegação e contexto de evento
- **D-09:** `AppLayout` deve migrar para o shell claro do redesign: sidebar/header mais contidos, fundo quente, superfície branca, bordas sutis e ações no header.
- **D-10:** O design introduz um `EventPill`/seletor de evento no header. Esta fase pode implementar a camada visual/estado local do seletor, mas não deve exigir backend novo se isso atrasar a migração.
- **D-11:** A navegação protegida deve preservar as rotas atuais: `/dashboard`, `/participantes`, `/inscricoes`, `/acomodacoes`, `/financeiro`, `/login` e `/register`.
- **D-12:** O shell precisa de breakpoint novo para mobile: não depender de sidebar fixa em telas pequenas; usar navegação recolhida, bottom nav ou drawer responsivo conforme melhor encaixar no código.

### Migração de páginas existentes
- **D-13:** Migrar visualmente as páginas existentes para o novo sistema sem mudar seus contratos funcionais principais.
- **D-14:** Dashboard deve seguir o modelo do redesign: banner de evento em andamento, métricas em cards claros, inscrições recentes e acesso rápido.
- **D-15:** Participantes deve migrar para toolbar com busca, `FilterTabs`, tabela/listagem clara e drawer de cadastro/ficha alinhado ao redesign, mas CRUD completo permanece Phase 7.
- **D-16:** Inscrições e Financeiro devem receber os padrões visuais de cards, tabelas, métricas, badges e progresso do redesign sem adicionar novas capacidades fora das fases 8-9.
- **D-17:** Acomodações deve absorver os tabs `Mapa visual` / `Estrutura`, cards claros e filtros por gênero, preservando a lógica existente de mapa, atribuição e estrutura.
- **D-18:** Login deve migrar para o layout editorial dividido do redesign, preservando Better Auth client e estados de erro/loading reais.

### Responsividade, acessibilidade e operação
- **D-19:** Mobile-first continua obrigatório; botões e ações críticas devem manter alvos de toque confortáveis, idealmente 44-48px.
- **D-20:** Tabelas do protótipo precisam de alternativa mobile aceitável (cards/lista responsiva ou overflow cuidadosamente tratado), porque o uso em contexto de retiro pode acontecer em celular.
- **D-21:** Estados `loading`, `error`, `empty` e offline grace devem ser tratados em cada página migrada; protótipo estático não é suficiente.
- **D-22:** Cores de status devem seguir o novo mapa sem perder semântica: success verde, warning âmbar/marrom, danger vermelho, info azul, neutral quente.

### Não regressão técnica
- **D-23:** Não quebrar Better Auth, `ProtectedRoute`, `AuthProvider`, `apiFetch`, TanStack Query ou cache persistido.
- **D-24:** Não introduzir dependências novas para o redesign salvo se o planner provar que as primitives atuais e Tailwind não resolvem limpo.
- **D-25:** Não alterar regras de domínio, endpoints, payloads ou permissões nesta fase exceto se necessário para manter uma tela existente renderizando após a migração.

### the agent's Discretion
- Escolha exata do padrão mobile do shell (`drawer`, `top nav`, `bottom nav`) desde que preserve navegação rápida e auth state.
- Granularidade dos componentes compartilhados e nomes dos variants em Tailwind.
- Ordem de migração das páginas, desde que login/shell/tokens venham antes das páginas dependentes.
- Manter ou substituir ícones `lucide-react` por Material Symbols conforme compatibilidade e custo de mudança.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `apps/web/src/components/ui/button.tsx`, `card.tsx`, `input.tsx`, `label.tsx`, `sheet.tsx`, `alert.tsx` — primitives atuais podem virar base do novo visual.
- `apps/web/src/components/layout/AppLayout.tsx` — ponto central para trocar shell/sidebar/header sem editar todas as páginas de uma vez.
- `apps/web/src/pages/dashboard.tsx` — já usa dados reais de participantes, financeiro, eventos e inscrições; migrar visual mantendo queries.
- `apps/web/src/pages/AcomodacoesPage.tsx` e `components/acomodacoes/*` — módulo mais sensível por já ter lógica operacional e deve ser migrado com cuidado.

### Established Patterns
- Rotas autenticadas passam por `ProtectedRoute`.
- Server state usa TanStack Query e `apiFetch`.
- Projeto usa Tailwind, CSS variables e shadcn-like primitives simples.
- Better Auth é canônico; não reintroduzir Supabase Auth.

### Integration Points
- `index.css` e `tailwind.config.js` são o primeiro ponto de migração de tokens.
- `AppLayout.tsx` deve receber o novo shell e breakpoint mobile.
- Páginas devem migrar depois do shell, preservando seus hooks e `apiFetch`.
- Login/register precisam preservar `AuthProvider` e redirects existentes.

</code_context>

<specifics>
## Specific Ideas

- O protótipo usa botões com borda 7px, cards com raio 10-12px, superfícies claras e foco com `goldLight`.
- O `EventPill` no header é uma boa peça de produto, mas pode começar como seleção visual/estado local até a Phase 8 conectar gestão de eventos completa.
- A tabela clara de participantes do redesign é mais alinhada à operação do que os cards escuros atuais; em mobile, a tabela deve virar lista/card para não degradar o uso.
- O login editorial "Gestão que libera para o essencial" deve orientar tom e hierarquia visual, mas o formulário precisa usar autenticação real.

</specifics>

<deferred>
## Deferred Ideas

- Check-in QR completo e overlay funcional pertencem a uma fase futura; o redesign mostra referência visual, mas não deve entrar no escopo da Phase 6.5.
- Criar novo evento a partir do `EventPill` pode ficar como ação visual/desabilitada até a Phase 8.
- CRUD completo de participantes fica na Phase 7.
- CRUD completo de eventos fica na Phase 8.
- Pagamentos/inscrições funcionais ficam na Phase 9.
- Offline mutation queue e hardening profundo de acomodações ficam na Phase 10.

</deferred>
