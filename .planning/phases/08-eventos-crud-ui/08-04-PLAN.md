# 08-04 - Eventos page CRUD UI and final verification

<objective>
Deliver the protected `/eventos` route with event list, status/capacity cards, admin-only create/edit drawer, and final frontend verification.
</objective>

<threat_model>
Event create/update can affect operational registration flows. UI must hide write controls from non-admins but still rely on backend admin-only enforcement. Form errors must not expose stack traces. Severity: medium before verification, low after RBAC-aware UI and API error handling.
</threat_model>

<must_haves>
  <truths>
    - `/eventos` is a protected route.
    - User can list events with name, dates, local/capacity, status, and capacity bar.
    - Admin can create and edit events through a drawer.
    - Non-admin users cannot access write affordances.
    - Capacity bars use backend `inscritos_count` and `ocupacao_percentual`, not fake local occupancy.
  </truths>
  <artifacts>
    - `EventosPage`
    - `EventoCard`
    - `EventoForm`
    - status display helper
    - protected route registration
  </artifacts>
  <key_links>
    - `App.tsx` routes `/eventos` to `EventosPage` through `ProtectedRoute`.
    - `EventosPage` consumes `useEventos`, `useCreateEvento`, and `useUpdateEvento`.
    - Mutations invalidate event queries from `use-eventos.ts`.
  </key_links>
</must_haves>

<decision_coverage>
- D-11: `/eventos` is added as a protected route in `App.tsx`.
- D-15: EventosPage cards follow operational card layout, status, dates, local/capacity, and actions.
- D-16: status filters use the approved FilterTabs visual contract.
- D-17: create/edit use a Sheet/Drawer aligned to the approved drawer contract.
- D-18: event write actions are admin-only in the UI and backend remains canonical.
- D-24: UI uses runtime `StatusEventoEnum` values exactly.
- D-25: display labels map enum values without changing backend statuses.
- D-26: capacity display uses backend-provided counts/percentage.
- D-27: CheckinOverlay and QR visuals remain reference only.
- D-28: no fake frontend check-in persistence is implemented.
</decision_coverage>
